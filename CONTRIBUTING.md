# Contributing

This guide covers the local gate, the branch and commit conventions, how decisions get recorded, and the review flow.

New to the codebase? Start with [`docs/architecture.md`](docs/architecture.md) — it is the code-verified developer guide, and every `src/knotica/...` path it cites is checked by `make verify`.

## Setup

```bash
uv sync --extra evals        # deps + the project, editable; the extra adds eval/compile/loop support
pre-commit install           # ruff, strict mypy, secret scan, id-citation discipline, diagram regen
sh scripts/install_git_hooks.sh   # ADR finalize hooks (idempotent; safe to re-run)
```

The `evals` extra is not optional for development: `make verify` runs the whole chain under `--extra evals`, and the test suite imports code that lives behind it.

## The gate

`make verify` is the canonical chain. Run it before every commit, and fix at each step before moving on — the three leading checks are cheap, and a failure there makes everything below it untrustworthy.

| # | Step | What it protects |
|---|---|---|
| 1 | `scripts/test_group.py --check` | Test topology in `.ai-state/TEST_TOPOLOGY.md` still matches the suite |
| 2 | `scripts/check_adr_health.py` | ADR frontmatter, cross-references, and index consistency |
| 3 | `scripts/check_architecture_coverage.py` | Per-package module counts and every cited `src/knotica/...` path in the two architecture docs |
| 4 | `mypy src/knotica` | Strict type checking |
| 5 | `pytest` | The full suite (~5 minutes) |
| 6 | `ruff check .` | Lint |
| 7 | `ruff format --check .` | Formatting — verifies, does not rewrite |

For the inner loop, skip the full suite:

```bash
make test-groups                 # list the scoped groups
make test-group GROUP=<id>       # run one, in seconds
make test-group GROUP=<id> ARGS="-x -q"
```

Group membership is derived from [`.ai-state/TEST_TOPOLOGY.md`](.ai-state/TEST_TOPOLOGY.md) and is never restated elsewhere. `make help` lists every target.

> [!IMPORTANT]
> **CI runs this same chain, on Python 3.12.** [`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs all seven steps above, in this order, on every push and PR to the default branch. It pins the interpreter to the `requires-python` floor rather than the 3.13 you likely develop on, so CI can fail on a step your local run passed — that gap is the point, since it gates the contract the package publishes. Run the chain locally anyway: catching a failure in seconds beats catching it in a red build, which is also why the pre-commit hooks carry ruff and strict mypy.

### Pre-commit hooks

`pre-commit install` wires six checks. Two are worth knowing about:

- **ruff runs without `--fix`** on purpose — the hook reports what the gate would report rather than silently rewriting the diff you are committing. Run `uv run ruff check --fix` by hand when you want auto-fixes.
- **`diagram-regen`** fires only when a `.c4` model is staged. It *regenerates and stages* the SVGs so a model change and its renders land in the same commit, and it refuses rather than committing a diagram whose model has unresolved references. It skips itself when `likec4`/`d2` are absent, so you are never blocked for lacking the toolchain.

> [!WARNING]
> Keep the pinned and installed ruff versions equal. When a hook rewrites a file and the versions disagree, pre-commit's own stash/restore cycle never converges — each attempt reformats, the restore reverts it, and completed work can vanish while `git status` reports a clean tree.

## Branch and commit conventions

- Branch off the default branch: `feat/<topic>`, `fix/<topic>`, `docs/<topic>`.
- One logical change per commit. Keep refactoring separate from behavior change.
- Stage files by name. Avoid `git add -A`; review `git diff --staged` before committing.
- Commit message format:

  ```
  <type>[(<scope>)]: <imperative subject under 50 chars>

  <body — what and why, wrapped at 72 chars, when context is needed>
  ```

  `type` is one of `feat`, `fix`, `refactor`, `docs`, `test`, `chore`. The
  optional `scope` names the subsystem a change lands in — `fix(loop)`,
  `feat(dashboard)` — and is free-form rather than drawn from a fixed list, so
  it cannot drift out of date as the package layout moves. Commitizen derives
  the next version from the `type` alone, so adding a scope never changes which
  release a commit produces.
- Never commit secrets, credentials, or generated build artifacts. `detect-secrets` runs at commit time against `.secrets.baseline`.
- No AI-authorship trailers (`Co-Authored-By: Claude`, `Generated by`, …) — the human owns the commit.

## Architecture and decisions

Structural changes carry documentation obligations, and two of them are gated:

- **Both architecture documents move together.** [`.ai-state/DESIGN.md`](.ai-state/DESIGN.md) is the design canon (intent, invariants, rationale); [`docs/architecture.md`](docs/architecture.md) is the developer guide (current state). Adding or removing a module changes a package's count, and `check_architecture_coverage.py` will fail until the inventory matches.
- **Decisions are ADRs.** Write new ones as fragments in `.ai-state/decisions/drafts/`; the finalize hooks promote them to numbered `<NNN>-<slug>.md` records when they land on `main` and regenerate `DECISIONS_INDEX.md`. Never point a finalized record at a `dec-draft-<hash>` id — the ADR health check rejects it. Never hand-number a draft either, though that one is on you: the check validates drafts only far enough to parse their frontmatter, so a draft carrying `id: dec-999` passes and collides at finalize.
- **Diagrams** live as source in `docs/diagrams/architecture/src/` and are embedded as rendered SVG. Inline mermaid/c4/d2 code blocks are not used in committed documentation.

## Documentation

Docs are ground-truthed against the code, not against other docs. When you change behavior, update the page that describes it — [`docs/reference.md`](docs/reference.md) for a command, flag, or tool; the relevant feature page for a mechanism; [`README.md`](README.md) only if the change is visible at the entry point.

State defaults explicitly. A flag documented without its default is half-documented.

## Pull requests

1. Push your branch and open a PR against the default branch.
2. Run `make verify` locally before pushing. CI re-runs the same chain on the PR, but a local run is faster and keeps the branch history free of fix-the-build commits.
3. Keep the PR focused; describe *what* changed and *why*.
4. Address review feedback in follow-up commits.

## Releases

Releases are cut by **dispatching a workflow**, never by bumping locally:

```bash
gh workflow run release.yml --ref main -f increment=auto   # or patch | minor | major
```

`/i-am:release` does the same thing with preconditions checked for you.

[`.github/workflows/release.yml`](.github/workflows/release.yml) runs Commitizen on a clean runner, and that is the **only** mechanism in this repo that changes a version string. A local `cz bump` produces a tag and a version no workflow run accounts for, which is the divergence the single-mechanism rule exists to prevent. To see what a release *would* do without changing anything:

```bash
uvx --from commitizen==4.17.0 cz bump --dry-run
```

One release is one commit, and it moves four files before tagging them together:

| File | Why it moves |
|---|---|
| `pyproject.toml` | `[project].version` — the only version string a human writes |
| `uv.lock` | Records the project's own version; CI runs `uv sync --locked`, so a stale lock fails the build |
| `.claude-plugin/plugin.json` | Claude Code reads this as a **cache key** — installed copies serve the version it names |
| `CHANGELOG.md` | Regenerated into the same commit, so the tag documents its own version |

### What your commit type does

The bump is derived from the conventional commits since the last tag, and the project is pre-1.0 (`major_version_zero`), so a breaking change is still a minor bump:

| Commit | Bump | In the changelog? |
|---|---|---|
| `feat:` | minor | yes |
| `feat!:` / `BREAKING CHANGE:` | minor (would be major after 1.0) | yes |
| `fix:` · `refactor:` · `perf:` | patch | yes |
| `docs:` · `chore:` · `test:` · `ci:` · `build:` · `style:` | none | no |

A release whose commits are *all* from the bottom row bumps nothing and the workflow stops — that is correct, not a failure. It also means a real user-visible change committed as `chore:` is invisible twice over: it moves no version and appears in no changelog. Pick the type that describes the change, not the one that keeps the diff quiet.

### After the release

The external [`bit-agora`](https://github.com/francisco-perez-sorrosal/bit-agora) marketplace manifest carries its own `version` field for this plugin, and Claude Code treats it as the cache key. Bump it to match the tag you just cut — while the two disagree, installed copies keep serving the older plugin and nothing surfaces the gap to their users.
