Karpathy’s LLM-wiki pattern

What Is an LLM-Wiki?

A wiki is a set of linked notes — a personal encyclopedia you write and edit over time. Each page can point to others, so ideas connect instead of living in isolated chat threads.

An LLM-wiki is that same wiki, but an AI helps maintain it: it reads your sources, writes and updates pages, cross-references topics, and stores everything in a git-backed vault you own.

Karpathy’s pattern: not just search over files — the LLM compiles sources into persistent memory that compounds with every ingest. Compounding memory needs a way to un-compound a bad claim, or every error is permanent.

Decompile a claim out

Memory Guillotine — the inverse operation Knotica was missing. It is now built, and it does not end at removal: a weakened claim becomes a gap that feeds back into the compile-in direction.

Pitch → shipped

What Was Pitched, What Shipped

Punk user sovereignty: power over the agent’s accumulated memory — not a deletion button, but memory due process. That held. One design commitment did not.

Shipped as pitched

  • Put any claim on trial — knotica guillotine "<claim>" --topic <t>.
  • See every place it lives, with its role in each passage.
  • Inspect supporting and contradicting evidence.
  • Transparent verdict + risk score; dry-run is the default.
  • The five risk bands, unchanged, still published in code.

Changed on contact with the design

  • The patch is never applied. The pitch said “wiki pages are edited”. As built, guillotine/ is a read-only analysis layer — the diff is evidence rendered for a human, not an edit.
  • Because removal alone is the wrong end state. Deleting a claim leaves a hole where knowledge used to be. So an applied verdict files a gap instead, and re-grounding flows through the normal ingest path where a real source and a human approval are required.
  • Persistence lives outside the package — core/operations/guillotine.py owns the transaction, which is what keeps the analysis layer inward-arrow clean.

Memory due process

A Claim-Level Trial

Eight questions — answered before any edit lands.

1 Where does this claim appear?
2 Is it asserted, quoted, contradicted, or merely mentioned?
3 Which sources support it?
4 Which sources contradict it?
5 Which synthesized pages depend on it?
6 What would break if we removed it?
7 Delete, demote, quarantine, or annotate?
8 Can the action be reversed with one git command?

Search → classify → score → patch — four stages, composed by runner.run_guillotine; rendering and persistence sit outside it, in the adapters. As shipped, no page prose is ever rewritten — the diff is evidence for human review, never applied. Raw sources/ stay immutable for audit.

Outputs

Verdicts and the Risk Score

Risk score (0–100) is a triage helper, not “objective truth.” Add up triggered factors, clamp to 0–100, then pick a verdict band.

Score Verdict In plain English
0–25 KEEP Looks fine — no change needed.
26–45 QUALIFY Add “maybe” or attribution.
46–65 DISPUTE → DEMOTE Soften universal wording. Shipped refinement: the band recommends DISPUTE only when a refutation was actually found — otherwise it degrades to DEMOTE, because disputing with no counter-evidence is a stronger claim than the evidence supports.
66–80 RETRACT Walk back the claim clearly.
81–100 DELETE Remove unsupported synthesis.

Score goes up when…

  • Claim stated as absolute fact
  • Weak or single source
  • On overview / index pages
  • No counterevidence found

Score goes down when…

  • Already qualified or attributed
  • Quotes or refutations present
  • Multiple independent sources
  • Marked disputed in the wiki

Every verdict ships with a report, a diff, and a JSON record — one commit, one git revert. The bands above are unchanged from the original pitch: VERDICT_THRESHOLDS in guillotine/models.py still publishes exactly these five.

Integration · gap-fill spine

The Loop Closes: Retraction Becomes Research

The pitch stopped at “remove the claim.” What shipped turns a weakened claim into a task the system already knows how to finish.

1 · guillotine
Verdict applied

A weakening verdict — RETRACT, DEMOTE, DISPUTE, DELETE_UNSUPPORTED_SYNTHESIS — commits its report, diff and JSON in one transaction.

2 · gap queue
A hole is recorded

The weakened claim is filed as an origin="retracted" gap, in its own transaction and failure-isolated: filing can fail without failing the retraction that already landed.

3 · discovery
Sources are proposed

The gap joins the same queue the loop’s own regression classifier feeds. Discovery searches, enriches and ranks candidate sources for it.

Human approves, then ingest

A person approves a candidate; the gated ingest path re-grounds the claim in real evidence. No LLM writes prose into the wiki unreviewed.

This is the part that did not exist at pitch time. Memory Guillotine is not a delete key with paperwork — it is the entry point to a re-grounding pipeline. A claim that fails its trial does not vanish; it becomes an open question with a queue behind it.

As built · 2026-08-05

Using It Today

# Try a claim. Dry-run is the default — nothing commits. knotica guillotine "X causes Y" --topic optics # Widen the evidence sweep, or read it as data. knotica guillotine "X causes Y" --topic optics \ --include-sources --json # Commit the verdict and open the re-grounding gap. knotica guillotine "X causes Y" --topic optics \ --apply --verdict demote

What lands in the vault

  • A Markdown report, a .diff, and a JSON record under <topic>/reports/guillotine/.
  • A bullet in the root catalog — one commit for all four.
  • On a weakening verdict, a retracted gap in the P1 queue.

Design properties worth keeping

  • A trial cannot cite itself. paths.is_guillotine_report_path excludes prior reports from the evidence sweep, so yesterday’s verdict never becomes today’s support.
  • Read-only by construction. The package holds no transaction; the fitness suite enforces that write_text_atomic is callable only from core/transaction.py, codebase-wide.
  • One cross-domain edge, report.py → okf.frontmatter, one-directional and acyclic.
  • Nine modules, its own test group (guillotine-audit) — a scoped run takes seconds.

Not yet on the MCP tool surface: the guillotine is CLI-only today. A conversational surface is the obvious next step, not a shipped one.
